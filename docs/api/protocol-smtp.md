# SMTP на проводе

Источник правды этого документа — тексты RFC в [`docs/rfc/`](../rfc/), а не код: кода на момент
написания нет. Документ существует затем, чтобы тест можно было написать **до** реализации, и
чтобы в тесте стояла ссылка на строку RFC, а не «ну так принято».

Ссылки вида `rfc5321.txt:3498` указывают на строку в копии из `docs/rfc/`.

Скоуп — **сабмишн** (RFC 6409): клиент отдаёт письмо релею на 587/STARTTLS или 465/implicit TLS,
как правило с AUTH. Прямая доставка на MX вне скоупа (см. research, риск 4).

## 1. Кадрирование

* Разделитель строк — только `CRLF`. Голые `CR` и `LF` в передаче запрещены — `rfc5321.txt:763`.
* Команда с `CRLF` — не длиннее 512 октетов; расширения могут поднимать этот предел для своих
  команд — `rfc5321.txt:3498`.
* Строка ответа с `CRLF` — не длиннее 512 октетов — `rfc5321.txt:3504`.
* Строка тела письма с `CRLF` — не длиннее 1000 октетов, не считая точки, удвоенной для
  прозрачности — `rfc5321.txt:3510`.

Клиент, который умеет разрезать на строки, но не проверяет длины, проходит счастливый путь и
падает на первом длинном заголовке. Проверка длин — часть парсера, а не «валидация где-то выше».

## 2. Ответ сервера

```
reply       = *( code "-" [ text ] CRLF ) code [ SP text ] CRLF
```

* Многострочность определяется **дефисом сразу после кода**; последняя строка отделена пробелом
  или ничем — `rfc5321.txt:2642`, `rfc2920.txt:193`.
* Код — три цифры; первая задаёт исход (2 — успех, 3 — промежуточный, 4 — временный отказ,
  5 — постоянный), — `rfc5321.txt:2642`.
* При включённом `ENHANCEDSTATUSCODES` (RFC 2034) первым токеном текста идёт расширенный код
  вида `5.7.8`; его классы описаны в RFC 3463, реестр — RFC 5248.

**Правило, которое ломает наивную реализацию:** ответы сопоставляются с командами **счётом**;
сопоставление по коду ответа или по тексту прямо запрещено — `rfc2920.txt:177`. Поэтому парсер
отдаёт поток ответов, а сопоставлением занимается слой выше.

## 3. Фазы сессии

```
connect ──▶ 220 greeting ──▶ EHLO ──▶ [STARTTLS ──▶ EHLO] ──▶ [AUTH ──▶ EHLO]
                                                                    │
              ┌─────────────────────────────────────────────────────┘
              ▼
        MAIL FROM ──▶ RCPT TO (1..n) ──▶ DATA ──▶ <тело> ──▶ CRLF.CRLF ──▶ 250
              ▲                                                             │
              └──────────────── следующая транзакция ◀──────────────────────┘
                                                                     QUIT ──▶ 221
```

* Приветствие `220` приходит **до** любой команды клиента; отрицательное приветствие (`554`)
  означает, что сессия не состоялась.
* `EHLO` обязателен; `HELO` — только как откат для серверов без ESMTP.
* После успешного `STARTTLS` клиент **обязан** выбросить всё, что узнал до рукопожатия, включая
  список расширений, и заново послать `EHLO` — `rfc3207.txt:210`.
* То же самое после `AUTH`, если механизм включил security layer — `rfc4954.txt:297`.
* `RSET` сбрасывает текущую транзакцию, не трогая аутентификацию.

Отсюда главное требование к API: список возможностей сервера — значение, живущее внутри фазы.
Значение, полученное до `STARTTLS`, после него недействительно.

## 4. Команды первой версии

| Команда | Форма | Ожидаемый успех | Примечание |
|---|---|---|---|
| `EHLO` | `EHLO <domain-or-address>` | `250` многострочный | первая строка — приветствие, остальные — ключевые слова расширений |
| `STARTTLS` | `STARTTLS` | `220` | после `220` — рукопожатие; `454` — временный отказ, `rfc3207.txt` |
| `AUTH` | `AUTH <mech> [<base64 или "=">]` | `235 2.7.0` | `rfc4954.txt:699` |
| `MAIL` | `MAIL FROM:<path> [params]` | `250` | пустой путь `<>` — для отчётов о недоставке |
| `RCPT` | `RCPT TO:<path> [params]` | `250` / `251` | по одной команде на получателя |
| `DATA` | `DATA` | `354`, затем после точки `250` | |
| `RSET` | `RSET` | `250` | |
| `NOOP` | `NOOP` | `250` | точка синхронизации при PIPELINING |
| `QUIT` | `QUIT` | `221` | |

Ограничения на адреса: local-part ≤ 64 октетов, домен ≤ 255, путь целиком ≤ 256 —
`rfc5321.txt:3484`, `:3489`, `:3493`.

## 5. Передача тела: прозрачность

Перед отправкой строки, начинающейся с точки, добавляется вторая точка; приёмник её снимает —
`rfc5321.txt:3423`. Конец тела — `CRLF.CRLF`.

Это самое дешёвое место сделать дыру: строка `.` в теле письма без удвоения обрывает сообщение
посреди, и сервер примет обрубок как валидное письмо. Тест на это пишется первым.

## 6. Расширения, попадающие в скоуп

| Ключевое слово EHLO | RFC | Что даёт клиенту |
|---|---|---|
| `STARTTLS` | 3207 | апгрейд соединения на 587 |
| `AUTH <механизмы>` | 4954 | список SASL-механизмов сервера |
| `PIPELINING` | 2920 | группировка команд |
| `SIZE <n>` | 1870 | максимальный размер; `MAIL FROM:<…> SIZE=<n>`, отказы `452`/`552` — `rfc1870.txt:221`, `:232` |
| `8BITMIME` | 6152 | тело в 8-битной кодировке без перекодирования |
| `SMTPUTF8` | 6531 | не-ASCII в адресах и заголовках |
| `ENHANCEDSTATUSCODES` | 2034 | расширенные коды в тексте ответа |
| `DSN` | 3461 | `RET=`, `ENVID=` у `MAIL`; `NOTIFY=`, `ORCPT=` у `RCPT` — `rfc3461.txt:1475` |
| `CHUNKING` | 3030 | `BDAT <размер> [LAST]` вместо `DATA` — `rfc3030.txt:140` |

Вне скоупа v1: `BURL`, `FUTURERELEASE`, `DELIVERBY`, `MTRK`, `REQUIRETLS` (RFC 8689 скачан, но
это отдельная веха), MTA-STS и DANE (относятся к выбору маршрута, а не к клиенту сабмишна).

## 7. PIPELINING: правила группировки

* В группе где угодно могут стоять `RSET`, `MAIL FROM`, `RCPT TO`. `EHLO`, `DATA`, `VRFY`, `EXPN`,
  `TURN`, `QUIT`, `NOOP` — только последними в группе — `rfc2920.txt:137`.
* Клиент обязан проверить статусы **всех** команд группы. Отказ всем `RCPT` не даёт права
  считать, что `DATA` тоже откажет: если `DATA` принята, надо всё равно отправить одну точку —
  `rfc2920.txt:160`.
* Если клиент не читает ответы параллельно записи, группа обязана целиком помещаться в TCP-окно
  (обычно 4 КБ), иначе дедлок — `rfc2920.txt:183`.

Последний пункт — не про оптимизацию, а про форму транспорта: чтение идёт своей корутиной
независимо от записи, иначе PIPELINING нельзя включить безопасно.

## 8. Таймауты клиента

| Ожидание | Минимум | Где |
|---|---|---|
| приветствие `220` | 5 мин | `rfc5321.txt:3623` |
| ответ на `MAIL` | 5 мин | `rfc5321.txt:3631` |
| ответ на `RCPT` | 5 мин | `rfc5321.txt:3633` |
| ответ `354` на `DATA` | 2 мин | `rfc5321.txt:3647` |
| отправка блока данных | 3 мин | `rfc5321.txt:3651` |
| ответ на финальную точку | 10 мин | `rfc5321.txt:3656` |

Это **минимумы**, а не рекомендации: клиент, который ждёт меньше, нарушает спецификацию. Значения
по умолчанию берутся отсюда; урезание — осознанная настройка потребителя библиотеки.

## 9. AUTH: обмен

```
auth-command    = "AUTH" SP sasl-mech [SP initial-response] *(CRLF [base64]) [CRLF "*"] CRLF
initial-response= base64 / "="
continue-req    = "334" SP [base64] CRLF
```
— `rfc4954.txt:699`, `:721`, `:735`, `:737`.

Пустой начальный ответ передаётся как `=`; отмена обмена клиентом — строка из одной `*`
(`rfc4954.txt:194`). Коды: `235 2.7.0` успех, `432 4.7.12`, `454 4.7.0`, `500 5.5.6`,
`530 5.7.0`, `534 5.7.9`, `535 5.7.8`, `538 5.7.11` — `rfc4954.txt:573`…`:630`.

Механизмы и их RFC: `PLAIN` — 4616, `CRAM-MD5` — 2195, `SCRAM-SHA-1` — 5802, `SCRAM-SHA-256` —
7677, `OAUTHBEARER` — 7628; `LOGIN` стандарта не имеет, но без него не обходится ни один почтовый
провайдер, поэтому реализуется как совместимость. Подготовка логина и пароля — RFC 4013/8265.

## 10. Классификация ошибок для API

Три категории, различимые вызывающим кодом:

1. **Постоянный отказ сервера** (5xx) — повтор бессмыслен, письмо не уйдёт никогда в этом виде.
2. **Временный отказ** (4xx) — имеет смысл повторить позже; сюда же обрывы соединения.
3. **Отказ части получателей** — транзакция прошла, но не для всех: результат должен быть
   структурой «принятые / отвергнутые с кодом», а не исключением. Это следствие того же
   `rfc2920.txt:160`: провал всех `RCPT` не отменяет `DATA`.

Схлопывать (3) в исключение нельзя — потребитель теряет знание о том, кому письмо всё-таки ушло.
